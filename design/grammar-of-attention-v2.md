# Grammar of Attention — Operator’s Library v2

## Purpose

This collection is an **operational manual**, not a continuous essay. A chapter must let a reader enter at any point, identify the claim, retain a useful fact, find the decision, and return to work with an action they can test.

> The goal is not to make every page louder. The goal is to make the important things impossible to miss.

## The reading contract

Each complete chapter uses four reading modes in deliberate rotation.

| Mode | Reader need | Approved element | Frequency |
|---|---|---|---|
| **Anchor** | Understand what is at stake | Incident, sharp opening sentence, operational fact | Every section needs one clear anchor. |
| **Recognition** | Name the pattern | System Concept, Warning, direct contrast | One or two strong moments per chapter. |
| **Action** | Decide what to do next | Field Method, Operator’s Rule, configuration extract | At least one testable action path. |
| **Retention** | Remember the chapter later | Memorable Phrase, Pull Quote, Key Takeaways | Fixed sequence at the end of each chapter. |

## Density rules

A paragraph should usually perform one job. If it contains the incident, the explanation, the judgment, and the recommendation at once, split it.

| Rule | Standard |
|---|---|
| Opening | Begin with an observable incident, condition, or operational contradiction. Do not open with abstract exposition. |
| Paragraphs | Prefer 1–4 sentences. Preserve longer paragraphs only when the reader must follow a technical chain of reasoning. |
| Headings | Use headings as claims or questions, not neutral filing labels. |
| Facts | Give concrete conditions, observed effects, decision boundaries, and verification signals. Do not invent precise metrics to simulate authority. |
| Repetition | Repeat a central claim only when the wording changes its function: incident, concept, rule, and takeaway. |
| Visual elements | Add an element only when it changes how a reader sees, decides, or verifies. Decorative emphasis is prohibited. |

## Operational fact

The collection may use an **Operational Fact** as a compact, non-decorative attention marker. It has one purpose: state a hard-to-ignore condition that changes the reader’s mental model.

```markdown
::: operating-fact
A critical task that only one person can complete is not owned by the team.
:::
```

Use at most **two** Operating Facts per chapter. They must express a verifiable operating condition, not a slogan.

## Anti-narrative test

A chapter is becoming a narrative essay when the reader has to cross more than two short paragraphs before finding a named condition, a decision, a warning, a fact, or a test. Break that sequence.

The repair is not to add decoration. Replace a general explanation with one of the following: an observable condition, a direct contrast, a named pattern, a bounded decision, or a practical exercise.

## Chapter cadence

A strong chapter moves through this sequence without becoming formulaic.

| Position | Function |
|---|---|
| First pages | Incident and observable contradiction. |
| Middle | Pattern named, assumptions exposed, one or two facts that change the reader’s model. |
| Practical core | Method, configuration extract, decision path, or exercise. |
| Exit | Operator’s Rule, Memorable Phrase, Field Note, Pull Quote, Key Takeaways, Next Chapter. |

## Language rules

Write like an experienced operator explaining the system to another capable operator. Use active verbs, visible targets, bounded claims, and consequences that can be checked.

Avoid generic escalation such as “this is crucial,” “everything changes,” or “the only path.” Replace it with the specific failure path, target, decision, or evidence that makes the point true.

The reader should encounter sentences worth underlining, but every sentence must earn its emphasis through an operational consequence.

Do not use em dashes in manuscript prose. Prefer a full stop, colon, comma, or parentheses when the relationship needs to be made explicit.

## Decision gate before publication

Before a chapter is marked `draft`, verify the following.

| Question | Required answer |
|---|---|
| Can a reader name the chapter’s claim after scanning the headings and callouts? | Yes. |
| Does the incident show a concrete operating condition rather than a generic outage? | Yes. |
| Are facts and examples useful without fabricated precision? | Yes. |
| Does every visual element teach, decide, or verify something? | Yes. |
| Does the reader leave with one action they can run in their own environment? | Yes. |
| Is the end sequence complete and ordered? | Memorable Phrase → Field Note → Pull Quote → Key Takeaways → Next Chapter. |
